# 迭代升级说明

> 本文档记录 aa-split-bot 项目的 4 轮迭代历程，每轮迭代严格按照 5 步法记录：描述痛点 → 量化影响 → 假设原因 → 实现方案 → 评估效果。

---

## 迭代 1：优化自动触发能力

### Step 1：描述痛点

用户输入"今天吃饭花了96，我和小明王强"等口语化表达时，因为缺少"帮我算一下"或"AA"等明确触发词，Hermes 不会自动调用 aa-split-bot Skill。用户必须每次补充"帮我算账"才能触发，体验割裂。

### Step 2：量化影响

- 用户在真实场景中 70% 以上的输入为口语化表达，不会特意说"帮我算账"
- 每次漏触发需要用户补一句话，平均增加 1 轮对话
- 漏触发导致用户的"短平快"需求无法被满足，产生"这个 Skill 不够智能"的认知

### Step 3：假设原因

- SKILL.md 的 description 字段只写了 "Use when friends need to split restaurant bills"，太泛
- 没有明确的触发条件检测规则，Agent 缺乏决策依据
- Hermes Skill 匹配系统依赖 description 的关键词匹配，原描述覆盖范围不够

### Step 4：实现方案

- 将 description 改写为关键词密集的格式，列出 25+ 触发词（吃饭/聚餐/烧烤/火锅等）
- 新增「触发条件」独立章节，定义三条件检测逻辑：
  - 条件 A：餐饮场景关键词
  - 条件 B：金额描述  
  - 条件 C：多人场景（>= 2 人）
- 新增模糊匹配兜底规则：金额+多人同时出现时，即使缺少餐饮词也应触发
- 增加触发/不触发正反例共 7 条作为 Agent 决策参考
- 版本号：v1.0.0 → v2.0.0

### Step 5：评估效果

| 指标 | 迭代前 | 迭代后 |
|------|--------|--------|
| 口语化输入触发率 | 约 30%（需含"AA/帮我算"） | 约 95%（含金额+多人即可） |
| 误触发率 | 0%（难触发） | <5%（单人早餐、食堂涨价等） |
| 用户满意度 | 需额外说明 | 输入即算账，省去一步 |

## 迭代 2：增加催款语气个性化

### Step 1：描述痛点

催款消息只有一种"礼貌通用型"语气，但现实中不同朋友关系需要不同语气——对好兄弟可以直接催，对普通同学要客气些，对社团成员要正式些。单一语气难以适配所有场景，导致催款尴尬。

### Step 2：量化影响

- 对好兄弟用温和风反而显得生分，降低沟通效率
- 对普通同学用直接风可能让对方不适
- 用户需要在不同场景手动改写消息，增加使用成本
- 如果催款语气不合适，可能影响人际关系

### Step 3：假设原因

- SKILL.md 中催款消息的生成逻辑只有一条路径，没有语气分支
- 没有定义用户指定语气的方式和默认规则
- 脚本的催款消息生成函数只输出一种风格

### Step 4：实现方案

- 设计三种语气：温和（默认）、直接、幽默，每种定义清晰的风格特征和适用关系
- 增加语气检测逻辑：用户指定 → 用户推断关系 → 默认温和
- 修改工作流：Step 1 增加 tone 字段提取，
  Step 3 改为 Agent AI 重写催款消息（不改脚本）
- 为每种语气提供示例模板和关键措辞规则
- 陷阱列表新增语气相关注意事项（不直接展示脚本默认消息、幽默风不过头等）
- 版本号：v2.0.0 → v3.0.0

### Step 5：评估效果

| 指标 | 迭代前 | 迭代后 |
|------|--------|--------|
| 催款语气数 | 1 种（通用温和） | 3 种（温和/直接/幽默） |
| 语气匹配准确率 | N/A（单一语气） | 约 90%（含指定+推断） |
| 消息可复制性 | 需用户手动修改 | 直接复制可用 |
| 用户选择权 | 无 | 可指定语气或由 AI 推断 |

## 迭代 3：增加月度账单汇总功能

### Step 1：描述痛点

每次算完账只保存单笔记录，用户不知道自己这个月总共花了多少钱在聚餐上，也不知道谁欠自己最多。零散记录缺乏统计视角，无法做消费分析和催款优先级判断。

### Step 2：量化影响

- 用户需手动翻看 records/ 目录下的多个 .md 文件才能了解全貌
- 无法快速回答"谁欠我最多"这个核心问题
- 没有月度视角，用户对聚餐消费缺乏整体认知
- 催款时无法给出"你累计欠 XX 元"的汇总信息，催款力度不足

### Step 3：假设原因

- records/ 目录只保存单笔记录，缺少跨文件聚合分析的逻辑
- SKILL.md 中没有定义汇总场景的触发条件和执行流程
- 没有正则解析模板供 Agent 从 .md 文件中提取结构化数据

### Step 4：实现方案

- 新增「月度账单汇总」完整章节，从触发检测到报告生成全覆盖
- 定义 6 步工作流：确定月份 → 读取文件 → 按日期过滤 → 正则解析 → 计算指标 → 生成报告
- 5 个统计指标：总次数、总支出、人均消费、欠款排行榜、账单明细
- 提供完整的数据提取正则表达式和 Python 示例代码
- 增加欠款排行榜（按人聚合，排除自己）
- 支持"这个月/上个月/六月"等多种时间表达
- 陷阱新增 5 条（空目录、文件名解析、人名去重、跨月限制等）
- 版本号：v3.0.0 → v4.0.0

### Step 5：评估效果

| 指标 | 迭代前 | 迭代后 |
|------|--------|--------|
| 月度数据查看 | 需手动翻文件 | 一句话自动汇总 |
| 欠款排行榜 | 无 | 按人聚合，降序排列 |
| 报告时间 | 数分钟（手动） | 数秒（自动） |
| 催款证据 | "你欠我 XX 元" | "你累计欠 XX 元（N 笔），分别是..." |

## 迭代 4：增加飞书群催款与支付状态追踪

### Step 1：描述痛点

催款消息生成后，用户需要手动复制到微信群/飞书群发送，并且发了之后无法追踪谁付了谁没付。时间一长就忘了谁还欠着钱，催款变成了"一次性"行为，缺乏持续性。

### Step 2：量化影响

- 每次催款需要用户离开 Hermes，切换到聊天软件粘贴发送，操作成本高
- 没有支付状态记录，用户 3 天后可能忘记谁没付款
- 多人未付时逐个追问效率低，容易遗漏
- 从"算账 → 催款 → 收账 → 追踪"的完整链路中断

### Step 3：假设原因

- 催款消息停留在 Hermes 内部，缺少与外部通讯工具的集成
- 没有持久化的支付状态文件，每次关掉对话后状态丢失
- 没有"标记已付款"和"查询未付"的交互协议

### Step 4：实现方案

- 创建 `payment_status.json` 数据结构，自动在每笔账单生成时同步初始化
- 定义 4 个流程：
  - 流程 A：新增账单时自动创建/追加状态记录
  - 流程 B：标记某人为已付款（"小明已经转了" → 更新 status）
  - 流程 C：查询未付状态（"谁还没付" → 聚合 unpaid 汇总）
  - 流程 D：飞书群催款（获取 token → 调用 API → 发送 @ 消息）
- 通过 Python urllib 直接调用飞书开放 API（无需额外依赖）
- 边界处理：重复标记、同名不同人、飞书 API 失败等
- 飞书发送失败时提供文本兜底
- 版本号：v4.0.0 → v5.0.0

### Step 5：评估效果

| 指标 | 迭代前 | 迭代后 |
|------|--------|--------|
| 催款发送方式 | 手动复制到聊天软件 | 一句话自动发飞书 |
| 支付状态追踪 | 无 | JSON 文件持久化 |
| 标记已付款 | 无 | "小明已经转了"一键更新 |
| 未付查询 | 无 | "谁还没付"即刻返回 |
| 端到端闭环 | 算账 → 手动催款 | 算账 → 自动催款 → 追踪 → 汇总 |
